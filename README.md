## 结构

```text
.github/workflows/collect.yml   定时采集（每小时 :17）
scripts/collect.mjs             零依赖，Node 20+
test/collect.test.mjs           解析函数单测
data/<repo>/issue-<n>.json      采集结果
```

## 配置

1. 建 fine-grained PAT：仅授权目标仓库的 `Contents: read`、`Issues: read`、`Pull requests: read`。
2. 存为本仓库 secret `TARGET_READ_TOKEN`。
3. 目标仓库写在工作流 `env.TARGET_REPO`。

## 运行

```sh
TARGET_REPO=owner/repo TARGET_TOKEN=... OUT_DIR=data node scripts/collect.mjs
TARGET_REPO=owner/repo TARGET_TOKEN=... ISSUE=5 OUT_DIR=data node scripts/collect.mjs  # 单卡重采，覆盖已有文件
node --test
```

无 `ISSUE` 时全量扫描已关闭 Issue，已存在 `issue-N.json` 的跳过（幂等）。

**解析规则改动后，旧数据不会自动刷新**。已有文件被跳过，新旧口径会混在一起。必须逐个 `ISSUE=N` 重采，或在本地删除对应 JSON 后让定时任务重建。

## 字段口径

| 字段                | 含义                                | 解析失败               |
| ----------------- | --------------------------------- | ------------------ |
| `risk`            | Issue 正文 `风险：高/低`，容忍 `**高**`      | `unknown`          |
| `rework`          | commit 数 − 1，近似返工，**不等于 push 次数** | —                  |
| `qa.result`       | 最后一条含 QA 结论的评论                    | `qa: null`         |
| `qa.sha_match`    | 被测 commit 是否为 PR 当前 head 的前缀      | —                  |
| `qa.fail_count`   | 所有轮次中 `FAIL` 的条数                  | —                  |
| `scope`           | Issue `允许修改` 白名单 vs PR 改动文件       | 白名单解析不出则 `unknown` |
| `assertion_delta` | 测试文件新增减删除的断言行，启发式                 | 负数需人工复核            |

`unknown` 比例本身就是数据质量指标，不要用推断把它填满。

## 与初版方案的两处必要偏差

实跑真实数据后才暴露，两处都会让数据错而不报错：

1. **白名单有两种模板写法**：`- 允许：\`a.mjs\``单行，以及`允许：`后接`- \`a.mjs\``列表（Issue #2 用的是后者）。只认前者会让 #2 的`scope`变成`unknown`。解析在遇到 `禁止/依赖/状态同步\` 或下一个标题时停止，避免把禁止行的反引号读进白名单。
2. **QA 结论有两种写法**：`QA 结论：PASS`，以及首行裸写 `PASS`（PR #7 第二轮）。只认前者会把 #7 的最终结论错记成上一轮 `FAIL`。裸结论回退要求同一条评论里出现 `被测 commit`，否则不认。

## 自身变更规则

**`main` 没有分支保护，可直接推送。** 这是有意取舍，不是遗漏：

- 每小时采集必须直推 `main` 才能落地数据。开了「要求 PR」的保护，自动提交会被拒，采集链断掉。
- 因此「改脚本先开 Issue、带测试、走 PR」是约定，**不是强制**。谁有写权限都能直推。
- 真要强制执行，得把数据提交改成「开 PR + 人工合并」，代价是每小时一次人工操作。当前样本量（3 条）下不划算。

最低可执行约束写进了代码：`scripts/collect.mjs` 顶部有醒目提示，每条正则上方标注守着它的用例名，`test/collect.test.mjs` 头注释说明改用例等于改口径。约束跟着代码走，不靠这份 README。

**元测试（第 22 个用例）只做格式检查**：每条顶层正则上方有 `// test:` 注释，且注释里的用例名确实存在于测试文件。它**不证明注释指向的用例真的覆盖那条正则**——注释可以指向一个存在但毫不相干的用例，测试照样绿。它的作用是防止约束退化成一句空话，不是保证约束有效。

因此「22 个测试通过」的含义到此为止：解析函数在给定输入上的行为被固定住了，不等于解析结果正确，也不等于覆盖了真实数据会出现的全部形态。把这两件事混为一谈，比没有测试更危险。

## 解析规则冻结（2026-10-22 起）

`scripts/collect.mjs` 的解析规则冻结。解除需要**同时**满足两个条件：

1. `data/MarketPulse-AI/` 至少 10 个 `issue-N.json`。
2. 至少一个**真实阳性样本**：下列任一信号出现在已采集的 JSON 里，**并且**已按下文方式人工核实。

   - `qa.sha_match === false`
   - `scope === "violation"`
   - `assertion_delta < 0`

   这三种信号的解析失败概率较低，但**不是不会误产生**：QA 把 commit 写错位数会得到假 `false`；白名单解析错位（比如把禁止行的反引号读进白名单）会误报 `violation`；断言计数把注释里删掉的 `assert` 也算进去，一次正常的注释调整就能得到负数。

   所以「人工确认」是解冻条件的一部分，不是形式条款。核实方式：

   - `sha_match === false`：打开 PR 评论，找最后一条 QA 结论里的 commit 原文，与 PR 头部 SHA 逐字符比对。
   - `scope === "violation"`：对照 PR 的 Files changed 逐个文件，回 Issue 正文确认白名单原文。
   - `assertion_delta < 0`：打开 Files changed，确认被删的是真断言还是注释。

   **不要用重跑 `collect.mjs` 的方式核实**——它和被质疑的解析是同一套逻辑，跑十次还是同一个错误。

   任一信号出现都走这套核实，不因为「这类信号看起来可靠」就直接解冻。

只满足第 1 条不解冻。10 个全是正常路径，等于没有任何数据能验证检测规则——解冻后照样不知道它能不能用。

`qa: null` **不算**阳性样本：分不清是"这个 PR 确实没做 QA"还是"QA 写了但解析不出来"。前者是流程信号，后者是解析缺陷，混在一起无法判断该修哪边。

这个条件的代价是可能等很久。等不到时需要先分清：流程真的没出过问题，还是规则根本抓不住问题。这两种情况的处理方式完全相反。

冻结原因：3 条样本就触发了两轮修订（白名单写法、QA 写法，随后收紧裸结论、改多轮取最后）。改得比样本快，数据就永远无法用来判断任何事——每次改动都让历史数据换口径，积累失去意义。

解冻后，每次改动必须附一个**真实失败样本**：某个已采集的 JSON 确实算错了，并能指出错在哪一行输出。"这种格式以后可能会出现"不算理由。

冻结期内要做的事：让目标仓库继续跑流程、继续关 Issue。不做的事：改解析、加字段、写 summary。

### 冻结范围外的例外：运行故障可以修

冻结的是**解析口径**，不是代码本身。采集脚本自己跑挂会让数据停止积累，直接破坏冻结的前提，所以必须能修。

判定标准只有一条，二分：

| 现象                            | 归类       | 处理       |
| ----------------------------- | -------- | -------- |
| 采集崩溃，该 Issue 的 JSON 没有写出来     | 运行故障     | 可以修      |
| JSON 写出了，但某个字段的值不对            | 解析问题     | 冻结，不能修   |
| 用 `unknown` / `null` 兜住异常让它跑完 | 等于新增取值规则 | 算解析改动，冻结 |

第三条是这条例外最容易被滥用的入口：把 `null` 当成 `unknown` 处理，看起来是容错，实际是决定「算不出来时该写什么」，那就是口径本身。

所以动手前先回答一句：**这次修改会让任何一个字段多出一种新的取值路径吗？** 会，就停，按解析规则走冻结流程。

修的时候三个条件：

1. 改动只落在 `get` / `all` / `main` 的流程控制上，`parse*`、`inScope`、`assertionDelta` 一行不动。
2. `risk`、`qa`、`scope`、`assertion_delta` 的判定逻辑不变。
3. 修完在下面记一笔，精确到可复查。

运行故障记录表目前为空，说明还没崩过——也意味着这条例外从未被真正验证。第一次用到时记录必须写到这个粒度，否则以后没人能判断那次修改有没有越界：

> 崩在哪：`all('/pulls?state=all')` 第 2 页>   
> 服务端返回：HTTP 502，`{"message":"Server Error"}`>   
> 现象：`Error: 502 ...` 抛出，该 Issue 无 JSON 产出>   
> 改动：仅 `get()` 增加 3 次指数退避重试，未触碰任何 `parse*` 函数>   
> 未验证：重试期间上游是否可能重复计数

## 未验证项与已知上限

下面这些是**已知限制，不是待修 bug**。等真实样本出现再动，冻结节优先。

单测固定的是解析函数在给定文本上的行为；真实仓库只出现过 3 种形态。以下情况**没有真实样本**，行为由单测锁定，但是否符合真实意图未验证：

| 情况                        | 当前行为                          | 风险                                               |
| ------------------------- | ----------------------------- | ------------------------------------------------ |
| 一条评论贴多轮 QA，结论与 commit 交错  | 结论取最后一轮，commit 取最后一个          | 最后一轮结论后又追加了下一轮 commit 时会配错                       |
| 裸结论（无 `QA 结论：` 前缀）前面还有标题行 | 判 `null`                      | 真结论被丢掉，记成 `qa: null`                             |
| 评论里粘贴的测试日志含孤立 `FAIL` 行    | 不算结论（只认首行）                    | 首行本身是日志时会误判                                      |
| `assertion_delta`         | 按 `assert`/`expect` 字面量计数     | 注释里提到的也算；大文件无 `patch` 时漏计                        |
| `sha_match` 遇到短 SHA       | 被测 commit 是 head 的前缀即判 `true` | QA 只写 7 位时，「前缀碰巧一致」也会记成匹配。冲突概率低但不是零，且无法与「真的匹配」区分 |
| 多个 PR 关联同一个 Issue         | 全部收录，不做取舍                     | 无法判断哪一个是主 PR                                     |

其他上限：

- 只覆盖 GitHub 上可见的行为；对话决策、本地操作不在数据里。
- `rework = commit 数 − 1`，不等于 push 次数。
- 公开仓库 60 天无活动会暂停定时任务；本仓库每次提交数据即算活动。
- 14:52 那次独立复核只覆盖 3 条正常路径样本，**不能**用来证明上面这些异常输入不误判；异常输入只有单测证据。
